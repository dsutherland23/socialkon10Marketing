# PHASE 4 — DUAL-MODE CHECKOUT ARCHITECTURE

## PRIMARY REQUIREMENT

Implement a configurable checkout architecture with three supported modes:

**MODE A — ORDER REQUEST**

Customers submit their shopping carts without paying online.

**MODE B — ONLINE PAYMENT**

Customers pay using a verified integrated payment gateway.

**MODE C — HYBRID**

Customers choose between immediate online payment and submitting an unpaid order request.

### Initial configuration

Set the website's active checkout mode to:

`ORDER_REQUEST`

The online payment mode must remain disabled until a supported payment gateway is configured, verified, tested, and explicitly enabled by an authorized administrator.

Do not attempt to charge credit cards or collect card information while the gateway is disabled.

### Architecture requirement

Use one shared system for:

- Product and service catalog
- Shopping cart
- Server-side pricing
- Discounts
- Taxes
- Order creation
- Customer information
- Order line items
- Administrative management
- Order history
- Notifications
- Reporting

Do not build separate disconnected order databases for each checkout method.

Separate the concepts of:

- Order status
- Payment status
- Fulfillment status
- Checkout method

The checkout mode must be configurable without code modifications or redeployment where the architecture supports runtime settings.

Store checkout configuration securely on the server. Client-side settings must not be considered authoritative.

Protect configuration changes with administrator permissions, validation, and audit logging.

# PHASE 5 — ORDER REQUEST CHECKOUT

Create a professional checkout experience allowing customers to submit their carts without online payment.

## Customer Journey

1. Customer browses products and services.
2. Customer adds items to the cart.
3. Customer adjusts quantities and chooses available options.
4. Customer opens checkout.
5. Customer reviews the order summary.
6. Customer enters contact and project information.
7. Server validates current product details, availability, and prices.
8. Customer submits the order request.
9. Server saves the complete order transactionally.
10. System generates and stores a unique order reference.
11. Customer receives confirmation.
12. Admin sees the order in the dashboard.

### Checkout fields

Collect relevant information:

- Full name
- Email address
- Phone number
- Company name (optional)
- Selected products and services
- Quantity
- Selected options or variations
- Project instructions
- Desired completion date (optional)
- Delivery or collection preference, if applicable
- Delivery address, if applicable
- Artwork or supporting files, if applicable
- Additional comments
- Agreement to applicable terms and privacy notice

Minimize unnecessary fields and use appropriate validation.

Do not require customers to create accounts unless there is a genuine business requirement.

Support guest checkout.

### Submit button

When Order Request Mode is enabled, display:

**Submit Order Request**

Do not display "Pay Now" or falsely imply payment has been completed.

### Confirmation

After the server successfully commits the order, display:

**Your Order Request Has Been Received!**

Include:

- Unique order reference
- Summary of submitted items
- Total or estimated total
- Currency
- Date submitted
- Customer name
- Order status
- Clear next-step instructions
- Confirmation that no payment has been collected
- Option to copy the reference
- Option to print or download the order summary

Send a confirmation email if the email provider is configured.

Email delivery failures must not silently invalidate successfully saved orders. Track notification delivery independently.

### Reference number requirements

Use a human-readable identifier, for example:

`SK10-YYMMDD-RANDOM`

The actual production format must:

- Be generated on the server
- Be collision-resistant
- Have a database uniqueness constraint
- Avoid predictable sequential public IDs
- Never be treated as authorization
- Be separate from the internal database primary key
- Remain immutable

A customer knowing an order reference must not automatically gain access to the customer's personal information.

# PHASE 6 — ORDER DATA INTEGRITY & PRICING

Every order must store an immutable snapshot of the items submitted.

Create or adapt an order architecture containing appropriate records for:

### Orders

- Internal order ID
- Public order reference
- Customer ID when authenticated
- Guest customer information when applicable
- Checkout method
- Order status
- Payment status
- Fulfillment status
- Currency
- Subtotal
- Discounts
- Applicable tax
- Delivery/shipping fees when applicable
- Total
- Pricing confirmation status
- Customer instructions
- Submission timestamp
- Updated timestamp
- Relevant administrative metadata

### Order Items

- Order ID
- Original product/service ID
- Product/service name snapshot
- Description snapshot
- Selected options
- Quantity
- Unit price
- Discount amount
- Tax amount
- Line total
- Customization metadata
- File attachment references, if applicable

Use appropriately precise money types, such as integer minor units or fixed-precision decimal values.

Never use ordinary floating-point calculations as the authoritative method for financial totals.

Always recalculate prices on the server using trusted catalog data.

Never trust totals, discounts, taxes, or product prices submitted by the browser.

### Pricing requirements

Support two pricing classifications where relevant:

**Fixed-price product/service**

The customer sees a confirmed price based on current catalog configuration.

**Quote-required product/service**

The customer sees a clearly labeled estimate or "Quote Required" status until SocialKon10 confirms the final pricing.

Avoid making customers believe that an estimate is a final guaranteed price.

When a cart contains quote-required items, do not misrepresent the whole order as a confirmed total.

If product prices change after order submission, preserve the original submitted price snapshot.

Any revised amount must be recorded as an authorized order revision, not silently overwrite the original values.

Support applicable currency and tax rules according to configured business settings. Do not invent tax rates.
